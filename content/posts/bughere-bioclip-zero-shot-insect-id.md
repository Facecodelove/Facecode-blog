你拍一张虫子上传，两秒后页面返回「中华蜜蜂，置信度 0.989」。如果有人问「你们这个分类器训了多久」，答案是零——这个系统里 2000 个物种的「分类头」，是一份 6.1 MB 的 `.npy` 文件，权重里没有一个参数属于这 2000 个类。

这是 BugHere（本地昆虫识别 + 拍虫发帖的项目）的识别服务，用 BioCLIP 2 做零样本推理，跑在纯 CPU 上。下面三件事是这套方案真正的工作量：为什么干脆不训练分类器、2000 个标签在运行时怎么被用上、延迟怎么压。

## 一、为什么不训练分类器：类别是数据，不是权重

训分类器有个隐含前提：**类别集合在训练时就被冻结了**。想加一个物种，你得补标注、重训、重评测，然后祈祷旧类别别退化。而 BugHere 的类别恰恰是会变的——它按省维护清单，标签规模还能在后台调（`identify.label_size`，默认 2000，配置范围 1–20000）。

于是这个项目把类别放在了数据库里，而不是权重里。核心就是 `region_species` 上的两个字段：`is_label` 和 `label_index`。前者标记「这个种在当前地区的候选集里」，后者是它在标签矩阵中的行号。

行号必须连续这件事，是靠一条 SQL 保证的：

```sql
-- RegionSpeciesMapper.xml:123-132（MyBatis 的 #{regionCode} 在此内联为实参，可直接执行）
UPDATE region_species rs
JOIN (
    SELECT id, ROW_NUMBER() OVER (ORDER BY occurrence_count DESC, species_id ASC) - 1 AS idx
    FROM region_species
    WHERE region_code = 'CN-GD' AND is_label = 1
) t ON t.id = rs.id
SET rs.label_index = t.idx
WHERE rs.region_code = 'CN-GD'
```

**为什么这条 UPDATE 是全文的支点**：在线推理做的是「图像向量 @ 文本矩阵」的一次矩阵乘，第 i 行的输出就是第 i 个物种的分数。所以「矩阵行序 ↔ json 里 labels 数组的次序」必须严格一致，否则分数张冠李戴。这个一致性不靠人工维护，而是靠 `ROW_NUMBER() - 1` 把排序结果直接写成行号；导出脚本还会校验 `indexes != list(range(len(labels)))` 就退出。换标签集免于重训，可行性就压在这一行 SQL 加一行 assert 上。

于是「新增一个物种」的完整链路是：后台翻转 `is_label` → `syncLabelIndex` 重排 → 重跑一次导出 → 重启识别服务。权重文件一个字节都没动。

那重训的成本到底是多少？BioCLIP 2 的训练数据是 TreeOfLife-200M，约 2.14 亿张图、覆盖 95.2 万个 taxa，训练用了 4 节点共 32 张 H100-80GB，跑 30 个 epoch、耗时 10 天（来源：HuggingFace 模型卡）。更关键的是仓库里没有训练所需的东西：全仓没有 train 脚本，唯一成体系的物种数据是 GBIF 名录（只有名字和分类，没有图），评测图集是 21 张 research + 205 张随手拍。

**但零样本不是免费的**：模型卡自己写了两条限制，一是零样本分类的前提是「你手里已经有物种名」，二是训练数据长尾、预测偏向样本充足的物种。这正好解释了项目的两个设计动作——先拉 GBIF 名录当标签来源，以及「低分一律降级为『未能确定到种』」。零样本省掉的是标注和训练，不是数据工程。

## 二、2000 个标签怎么用

### 2.1 从 4591 收窄到 2000，再把标签变成向量

广东的 GBIF 清单有 4591 个种，按出现记录数取前 2000 个置 `is_label=1`。反直觉的是，**限制标签数不是为了省时间**。项目实测 209 个标签和 5000 个标签的单图耗时是 1.50 s 对 1.57 s——在线只跑视觉塔，文本矩阵大小只影响一次点积，2000×768 也就 154 万次乘加。收窄的理由是精度：候选集越大越容易混淆，而本省真会被拍到的物种本来只有这么多。

标签转文本时用的是**拉丁学名**而不是中文名：

```python
# scripts/export_labels.py:80
texts = [f"a photo of {item['latinName']}" for item in labels]
```

**为什么是学名**：中文名存在同名、异名、俗称的问题，学名在分类学上唯一且稳定；中文名只留在 json 里给前端展示。顺带一个细节：2000 条里有 1439 条中文名为 `null`，界面显示「暂无中文名」而不杜撰译名。

导出后产物是 `infer/labels/CN-GD.npy`，实测 6144128 字节，正好等于 2000×768×4（float32）加 128 字节 npy 头。在线加载时读成 `(2000, 768)` 矩阵再 L2 归一化一次，之后每个请求只拿它做点积。**这就是离线文本编码的全部收益**：文本塔一次都不进请求路径。量级可以看这组记录——209 个标签离线编码 9.0 秒，5000 个标签 557 秒；557 秒放进请求路径，这个接口就没有存在意义。

### 2.2 先判「是不是虫」，再判「是哪只虫」

只有 2000 路 softmax 时，一张鸟的照片会怎样？实测最高分 0.0923；植物照片 0.2042。**这不是模型不行，是 softmax 的性质**：鸟的正确答案根本不在候选集里，2000 个概率只能被摊薄撒给某个不相关的小虫，而「最高分很低」本身没有明确的阈值含义。

所以判定分两级。第一级不用细标签，而是另编两组粗提示词——9 条昆虫提示词、20 条非昆虫提示词——比较两组的**最大 logit**：

```python
# infer/model.py:196-205（节选）
insect_group = (features @ self._insect.T).squeeze(0)
ood_group = (features @ self._ood.T).squeeze(0)
insect_best = float(insect_group.max())
ood_best = float(ood_group.max())

margin = float(os.environ.get("INFER_INSECT_MARGIN", "0"))
is_insect = insect_best + margin >= ood_best
```

**为什么不复用 2000 路 softmax 的概率分段**：组最大值只比较「最像昆虫」和「最像非昆虫」两条提示词谁更靠前，不要求正确答案在集合内——这正是开放集该有的形状。

这里有个必须交代的量纲坑。实测 6 张图的余弦差是：昆虫 +0.0268…+0.0338，植物 −0.0342，鸟 −0.0762。而 `logit_scale = 100.0`，乘过去变成 +2.68…+3.38 / −3.42 / −7.62 个 logit——代码注释里「昆虫高 2–4 个 logit、植物鸟低 3–8 个」说的就是乘过 100 之后的口径。**这直接决定 `INFER_INSECT_MARGIN` 怎么填：它的单位是余弦差，填 0.01 等于要求昆虫组领先 1 个 logit**。凭直觉填 `1`，就等于要求领先 100 个 logit，判定永远不会为真。

## 三、CPU 延迟怎么压

先拆清延迟的构成：模型加载 54.7–122.3 秒、启动预热 1.5–4.1 秒（都是一次性），再加上单图前向（每个请求）。只有第三项值得优化，前两项的正确做法是挪到启动阶段并由健康检查挡住——服务未就绪时 `/health` 和 `/predict` 都返回 503，主服务据此熔断。

### 3.1 线程数：6 是 P-core 的数量，不是拍脑袋

本机实测（i7-12650H，iNat research 图，取 P50）：1 线程 4072 ms（n=8）→ 6 线程 1596 ms（n=20，2.55×）→ 8 线程 1532 ms（n=20，快 4%，噪声内）。

**为什么拐点恰好在 6**：i7-12650H 是 6 个 P-core + 4 个 E-core 的混合架构，第 7、8 个线程会被调度到 E-core，而一次前向的所有线程得等最慢的那个。仓库曾记录「8 线程 2.4–2.9 s、6 线程 1.4–1.5 s」，我两次独立运行都没复现（8 线程反而略快）。所以稳的结论是「6→8 无收益，6 个 P-core 是拐点」，把「8 更慢」当某次记录而不是规律。

### 3.2 OpenMP 自旋：两个变量必须一起设，且在 import torch 之前

```python
# infer/app.py:13-20（节选，省略第 16–19 行的空行与标准库 import）
os.environ.setdefault("KMP_BLOCKTIME", "0")
os.environ.setdefault("OMP_WAIT_POLICY", "PASSIVE")
os.environ.setdefault("INFER_THREADS", "6")

import torch
```

**为什么是这两个变量、顺序为什么不能错**：`KMP_BLOCKTIME` 的定义是「线程完成并行区后、进入睡眠前等待的时间」，默认 200 ms；`OMP_WAIT_POLICY` 默认已是 `passive`，但 OpenMP 运行时文档明确写着：除非你显式设过 `OMP_WAIT_POLICY`，否则仍存在一段由 `KMP_BLOCKTIME` 决定的主动自旋。所以两个一起设才完整——一个把 200 ms 自旋清零，一个把等待方式钉死。至于顺序，torch 一被 import 就会初始化线程池，之后设环境变量等于没设。

代码注释里记过一次「不设时空载吃满 85% 单核」的观察；我做了 A/B（各推理 3 次后空转 5 秒比较进程 CPU 时间），两轮都是 0.00 s，**这个数字没复现**。所以只能把它当一次观察记录引用，不能写成已复现。

### 3.3 第三个手段：用排队换稳定

并发策略：`predict()` 用 `threading.Lock` 把整个前向串行化，进程内单例。

**为什么串行而不是并发**：6 个核已被一个前向吃满，再叠一个请求只会两个都变慢。项目在 Java 侧用两层缓存接住这个限制——同 `content_hash` 的 24 小时 Redis 结果缓存，以及进程内同图单飞；`/metrics` 暴露 `predict_calls`，验收脚本断言「并发请求同一张图时 Python 只被调用一次」。

另外：这个服务**没有**做批处理、量化、ONNX、TorchScript，也没有 GPU 路径，全仓 grep 为空——这些是未来方向。

## 收尾：这套方案真正换来了什么

零样本换来的不是「免费」，而是把成本从「标注 + 训练」搬到了「名录工程 + 提示词设计 + 延迟调优」。它买到的是可演化性：换一个省只是多一对 `.npy/.json` 文件，权重始终不动。代价是精度上限由模型决定，且必须靠产品规则接住：低分降级为「未能确定到种」。

最后留一个最容易被忽略的教训：**延迟数字必须带测量条件**。同一个项目、同一台机器、同一份权重，`docs/` 与 `scripts/eval/report.md` 里对同一指标就记过 0.50 s、0.51 s、0.61 s、0.72 s、0.918 s、1.46 s、1.50 s 一串数，另有 8 线程的 2.4–2.9 s；我这次复测又落到 1.53–1.60 s。写「2 秒内返回」是产品承诺，写「1.4 秒」是某个下午的某次测量——分不清这两者，优化就变成猜数字。
